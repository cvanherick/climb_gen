# ClimbGen beta

A simple climb generator for a fixed 40° Tension Board 2 Mirror problem. Choose a grade from V0 to V11 or leave it on Any. ClimbGen has its own dark-and-lime interface; the board map uses the authentic TB2 Mirror hold artwork and public community climbs from the BoardLib dataset.

## Run locally

Run `python3 scripts/build_standalone.py` to create self-contained `index.html`, `index.template.html`, and `index.source.html` files, then open `index.html` in a modern browser. `index.shell.html` is the shared build source. After editing the app, styles, data, or assets, rerun the standalone builder.

## Dataset

`data/tb2-mirror-40.js` contains the 498 actual base-set placements in the selected 12 × 12 Mirror layout and 3,027 eligible 40° community climbs. The route slice keeps listed single-frame climbs with at least three ascents and a quality average of 2.4 or higher, then filters to routes whose holds all exist in the selected layout and have one or two starts, three to five middle holds, one finish, and one to four foot holds. The authentic transparent wood and plastic placement images are in `assets/`; the standalone builder embeds them along with the data so both pages work offline.

The database and placement images were downloaded using BoardLib’s documented public data flow. BoardLib extracts the bundled database from the Tension Board Android app and downloads layout images from the Board API; syncing newer rows requires a Tension account, so this bundled slice reflects the app database version available at acquisition time. See [BoardLib](https://github.com/lemeryfertitta/BoardLib).

## Interactive 3D board

Choose **3D view** on the TB2 card, then reveal beta for a generated problem. Drag or use the arrow keys to orbit. Shift + drag pans, and scroll, pinch or the zoom buttons adjust distance. **Front**, **Side**, and **Reset** switch camera angles. The playback position slider pauses at the selected time, and the same playback position is used in both board views.

The 12 × 12 ft panel is set at 40° from vertical. All 498 holds use the app's installed Mirror coordinates. The [Tension Climbing installation index and CAD archive](https://tensionclimbing.com/pages/led-installation-guides) publish installation locations and planar panel drawings. The archive contains four planar DXF files. The hold meshes use footprints from the aligned board images, including two footprints rotated from the matching hold shape using its installation marker. Their depths and relief are estimated. Playback anchors hands and toes to the modeled contact surfaces. Rebuild the footprints with `python3 scripts/build_hold_geometry.py` (OpenCV and NumPy).

## On-demand climb generation

The browser now generates a new climb variant on every click rather than cycling through the 120-row prepared pool. `route_generator.js` selects a well-rated route template for the requested grade, keeps every start hold in the board's lower third (`y ≤ 44`), changes one to three hand or foot contacts using TB2 community hold frequencies, then checks upward progress, reachability, vertical spread, and isolated holds. Before displaying a route, the app also requires the four-limb beta planner to find a contact sequence; it retries other variants when a candidate fails. Quality-checked DDPM samples can also seed variants. It avoids repeats during the current page session. The possible combinations are very large but finite because the board has a fixed hold set.

`scripts/train_diffusion.py` trains the offline grade-conditioned DDPM from TB2 routes labeled V0–V11. Each route's grade is supplied to a learned grade embedding during denoising training; the model also receives classifier-free grade dropout so sampling can apply explicit target-grade guidance. The train/validation split is stratified by grade, underrepresented grades receive inverse-square-root sampling weight, and checkpoint selection uses macro-averaged per-grade validation loss. Sampling requests the selected grade, then rejects candidates that fail the same start, progress, spacing, and reachability checks used by the app. The browser does not need PyTorch or a backend: the fresh checkpoint's screened samples are bundled as grade-specific seeds, and on-demand variations draw replacement holds only from that same grade's TB2 statistics. `scripts/train_route_evaluator.py` separately trains a compact grade classifier and community-rating regressor from the route geometry and TB2 labels, and writes `data/tb2-route-evaluator.js` for browser inference. On the current holdout split the grade estimate has 1.09 V grades of mean absolute error; it is a ranking hint, not a replacement for the requested grade or climber feedback.

The generator plans a direction change, rising traverse, or setup and reach. It varies hand and foot placements around that idea, scores the candidate's grade and movement pattern, and compares the actual hand sequences of playable candidates. It excludes exact copies of bundled routes. The community rating data is quality-filtered and contains no negative labels for generated routes, so the score cannot reliably flag bad climbs; human ratings on generated problems are needed to learn that distinction. Route checks are geometric filters, not a real-world safety test.

The climb-style selector offers **Any style**, **Static**, and **Dyno-like**. Static biases the beta search toward shorter, controlled hand reaches. Dyno-like limits routes to at most three middle hand holds and two footholds, favors longer hand reaches, and ranks a small set of playable variants by those reach distances. Both retain the planner's ordinary limb-reach checks. This is runtime heuristic conditioning: the TB2 training rows do not label movement style, so the DDPM checkpoint uses grade and static hold-spectrum context, with style applied at runtime, and Dyno-like does not simulate a jump or momentum.

## Climb names and beta planning

The name entered in the app is the route title and one input to a per-session random seed. It does not have learned semantic meaning: the bundled BoardLib route rows do not contain climb names. Retraining on a dataset with route names would be needed for text-guided holds.

“Reveal beta animation” runs a bounded beam search over left and right hand and foot contacts. Each node includes the four contacts and a torso pose. The objective combines limb reach, joint-angle awkwardness, approximate support, body movement, repeated-limb moves, and move count; weights can be overridden through the planner API's `options.weights`. The planner supports hand matches, foot swaps, cross-through reaches, and high, lateral, or downward foot repositioning. It may return an explicit no-plan result when the search budget expires or it cannot satisfy the modeled reach constraints; it never substitutes the candidate's precomputed hand sequence.

`ik.js` contains the configurable body dimensions and two-bone IK solver. Reachable link lengths are solved exactly. The optimizer estimates torso position, joint angles, center of mass, and a support polygon; the 40° overhang scales a heuristic penalty only. `planner.js` is independent of the page DOM and yields between expanded states. During playback the climber shifts onto a supporting foot, rotates the hips and shoulders, then reaches or lifts a shoe and settles onto the new contact. The other contacts stay planted. The planner scores support at release and requires a two-hand finish match.

The result panel separates modeled kinematic checks from the approximate support score and states that physical feasibility is unverified. Debug details are hidden by default; open “Planner diagnostics” to view explored states, rejected transitions, timing, weighted cost, center of mass, and support hull. The planner retains up to three distinct low-cost contact sequences from the completed beam and lets the climber cycle through them. These are alternative outputs of the same geometric cost function, not learned or expert-validated beta.

## Build a climb from a wall photo

The experimental photo builder keeps an uploaded wall image in the browser session. After the user marks the wall's four corners, `photo_hold_detector.js` segments a single foreground mask against the dominant wall colors, closes tiny texture gaps, scores connected regions, and outlines each candidate. The wall mask excludes foliage, mats, and supports outside the climbing surface. Users can remove false marks, add missed holds, select a start, and choose among ranked next-hold options, including a possible finish. This remains an experimental image-segmentation heuristic, not a trained hold model; it can merge same-colored adjacent holds or miss shadowed/textured holds. Suggestions use corrected hold coordinates and TB2 community-route movement geometry as a prior. A single image does not establish physical wall angle or scale; angle input is optional and user supplied. Suggestions are not photo-conditioned diffusion and do not verify reachability or safety. `photo_suggestions.js` and `photo_hold_detector.js` are loaded by both Pages and standalone builds.

There are public image datasets that could seed a hold detector, but their rights need to be checked at the image-source level. The [Crimps Bouldering Holds dataset](https://universe.roboflow.com/crimps/bouldering-holds-rpoux) states CC BY 4.0 for its 427-image version; retain attribution and confirm export/model redistribution terms before bundling a trained model. [ClimbInst](https://huggingface.co/datasets/ClimbVision/ClimbInst) has more annotations, but defers to the licenses of its constituent image sources. Do not treat arbitrary web images or videos as training data simply because they are publicly viewable; [YouTube's developer policies](https://developers.google.com/youtube/terms/developer-policies/) prohibit scraping and downloading or storing audiovisual copies without prior written approval.

### Reproducible evaluation

Run `node --test tests/planner.test.js` for IK, deterministic route, and explicit failure tests. Run `node scripts/evaluate_planner.js` to benchmark a deterministic stratified sample (indices 0, 11, 22, …, 111) spanning V0–V11. On the current local run, the planner found a contact plan for 11 of 12 routes, with an average of 8.7 contact actions and 29 foot moves across those 11 plans. Search time ranged from a few milliseconds to 1.57 seconds on this machine. One case returned no plan within the configured model/search limits.

The evaluation also records the previous approach's prewritten hand-move count and simple hand-to-hand reach excursions. That baseline had 19 moves over a 36 board-unit point-to-point reach threshold across the same 12 routes. This is only a diagnostic of the old fixed sequence, not a learned or hand-labeled beta-quality benchmark. No ground-truth contact sequences are available in the bundled community rows, so these results do not establish that the new sequences match expert beta or are safe to climb.

### Limits and next research step

The contact search uses the board plane. Playback solves a spatial rig and projects it onto the same hold map. It uses geometric constraints and an approximate center of mass. Grip, friction, and dynamic forces remain unmeasured. The search state stores torso pose, but equivalent contact/visited states are canonicalized during pruning to control runtime. Explicit foot flags, temporary unweighting, force transfer, and 3D cross-through motion are not modeled. Names remain titles and deterministic route-pool seeds, not learned text conditioning.

### Motion-data direction

[ClimbingCap / AscendMotion](https://openaccess.thecvf.com/content/CVPR2025/html/Yan_ClimbingCap_Multi-Modal_Dataset_and_Method_for_Rock_Climbing_in_World_CVPR_2025_paper.html) is a possible future source for a learned movement prior. It is not integrated here; the next useful research milestone is to hand-label plausible four-limb sequences for a small TB2 route set and compare the geometric planner against those annotations before adding a learned motion model.

`scripts/prepare_motion_data.py` is a provenance-gated adapter for owner-permitted pose/contact annotations. It requires an explicit training permission flag and records dataset/license provenance. See [the motion-data schema](docs/motion-data-schema.md). It does not download videos, infer contacts, or establish dataset rights.

## Hold references and articulated climber

The supplied screenshot archive is imported by `scripts/import_hold_profiles.py` (requires Pillow). It joins all 498 crop/metadata rows to existing placement IDs 304–801, checks board coordinates at runtime, and converts image-space downward Y vectors to board-space upward Y. Full crops and the original metadata remain in `assets/hold-crops` and `docs/hold-references`; Pages uses a compact preview atlas. The supplied online CSV/gallery are reference links, not new training labels or downloaded imagery.

Hand-direction costs depend on the shoulder position relative to the hold. Unknown/rounded holds receive no directional penalty. Resolved screenshot estimates use a broad 80° unpenalized cone and 0.08 weight; reviewed directions use a 55° cone and weight 1. These are soft pose preferences; neither is a measured force capacity or a unique grip normal. Foot force directions are not inferred from hand-grip annotations. The planner uses these costs when scoring beta and therefore selecting playable generated routes. The diffusion and grade evaluator have been retrained with the separate provisional hold-spectrum metadata; screenshot pull-vector estimates remain runtime pose preferences.

Open **Hold direction references** under the board to inspect crops or show direction arrows. Import the supplied editor's exported JSON to apply reviewed directions; imports validate layout/IDs/numeric vectors, persist locally when storage permits, and invalidate cached beta for replanning. Screenshot-derived default estimates are never automatically marked reviewed.

Playback gives the pelvis a hanging position based on the wall angle and the active holds. The stance sets hip rotation, the knee joints bend toward the wall within a clearance limit, and the shoes keep their orientation while planted. The solver keeps the pelvis above the floor and adjusts it in three dimensions to preserve limb lengths. It favors flexed knees where the footholds allow and lets the climber extend on a wide stance.

The contact planner leaves room below the head for foot movement. Replay enforces five inches of clearance between the head center and the toes, heels and ankles in both the board projection and world height. It scores shoulder, elbow, wrist, hip, knee, ankle, spine, neck and finger angles when choosing the posture and movement path. The knee bend plane is adjusted and smoothed along its reachable circle to keep limb lengths exact and reduce snaps. The joint limits are simplified ranges for the avatar and allow movement preferences to differ from full passive mobility. [CDC joint range study](https://archive.cdc.gov/www_cdc_gov/ncbddd/jointrom/index.html) · [Climbing wrist and finger motion study](https://pmc.ncbi.nlm.nih.gov/articles/PMC11048272/).

In **3D view**, turn on **Show hold loads**. Cyan shows hand pull, purple shows foot push, and gold shows gravity. Select a contact row to pause and focus the camera on that hold. The hand and load arrow share a grip patch on the reconstructed hold. The patch uses the hold outline and any reviewed pull direction. Estimated patch width changes finger curl and the force direction model. The model fits gravity and torque about the center of mass at each pose and compares solutions with different contact loading assumptions. The panel reports magnitudes as percentages of body weight. These are model ranges for static balance. Actual forces during a move also depend on acceleration, grip, friction and climber strength. Frames without a plausible balance omit the contact estimates. [Measured climbing force distribution](https://doi.org/10.1007/s00421-025-06047-y).

The timing and posture are procedural estimates. The weight shift and lower-body drive draw on [Asakawa and Sakamoto’s comparison of climber counter-movements](https://doi.org/10.1589/jpts.31.349). Playback tests check contact drift, limb and shoe lengths, and joint continuity on a bundled climb. Matching a particular climber’s movement would require calibrated motion footage and body measurements.

### Animation regression checks

`node --test tests/animation.test.js` samples a bundled climb at 60 frames per second, checks planted-contact drift and limb lengths, verifies consistent bend branches and continuous move boundaries, and limits per-frame joint displacement. It also covers pause/resume, speed changes and background delays. These are geometric continuity checks; they do not establish expert movement quality or full physical feasibility.

## Manufacturer difficulty spectrum

`data/tb2-hold-spectrum.js` joins Tension's official [Mirror hold index](https://tensionclimbing.com/pages/hold-details-table-mirror-layout) and [Spray hold index](https://tensionclimbing.com/pages/hold-details-table-spray-layout) to all 498 BoardLib coordinates using `x=8*column, y=8*row-4`. Colored handhold circles from the user-supplied [manufacturer spectrum chart](https://tensionclimbing.com/blogs/blog/tension-board-2-built-for-progression) are transferred by material and physical hold family, including mirrored plastic pairs. The current extraction assigns provisional easy/intermediate/advanced/hard tiers to 364 placements. Missing or conflicting observations leave the other 134 hand tiers unknown. These are ordinal hold tiers, not V grades, and their 0.7 confidence values are heuristic influence weights, not calibrated probabilities. Installation compass markers orient the templates; they are not grip-force normals.

The chart's 11 foothold shapes were matched manually against named indexed hold crops. Their 20 approach options cover 98 placements, with provisional board-space angles pointing from the contact toward the hip. Foothold effort changes with body position and installed orientation. The planner uses this as a soft effort cost and keeps geometric reach constraints independent. It does not infer grip strength or friction from these tiers. The hold inspector shows tier coverage, unknowns, shape names and directional foot categories.

The evaluator now uses 28 features, including tier proportions, maximum hand tier, coverage, foot best/worst tiers, directional spread and material. Training and browser feature vectors are checked for numeric parity. On the identical seeded 603-route validation split, the 16-feature geometry baseline's grade MAE was 1.524 and the spectrum model's was 1.095; exact-grade accuracy rose from 19.4% to 26.2%. This is an initial internal holdout result on accepted community routes, not validation of individual hold labels or generated climb quality. Details are in `docs/hold-spectrum-training.json`.

The denoiser receives the target-grade embedding plus 12 static context channels per hold (confidence-weighted tier/coverage features, directional foot range, material, installation orientation). It aggregates the noisy role grid against these channels at each denoising step, so spectrum information participates during training and sampling. `models/tb2-spectrum-diffusion.pt` was trained for 50 epochs with the original grade-stratified split and classifier-free grade dropout. The regenerated browser pool contains eight screened diffusion variants plus two clearly marked community examples per grade. A lower denoising loss is not a measure of movement realism.

To reproduce labels, run `scripts/extract_chart_tiers.py` with the original 4338×4339 image (Pillow/OpenCV/SciPy required), then `python3 scripts/build_hold_spectrum.py`. Observation coordinates, official identity indexes and provenance are committed. Train with `python3 scripts/train_route_evaluator.py` and `python3 scripts/train_diffusion.py --epochs 50 --samples-per-grade 150`. Checkpoint weights remain in the local `models` directory; Pages serves the trained evaluator and screened diffusion seeds.

## Analyze a TB2 climbing video

1. Open **TB2 Climb Analysis** from the home screen and choose an MP4, MOV, or WebM your browser can decode. Use a fixed camera that shows the full 12 × 12 TB2 Mirror face at 40°, including the bottom corners. Aim for good lighting and keep other people out of the frame.
2. Enter the climber's height, with weight optional. Pause on a clear frame and choose **Mark board corners**. Click upper left, upper right, lower right, then lower left on the plywood face. Check the hold preview and choose **Apply corners**. To adjust the alignment later, select a handle and click its new position.
3. Select **Analyze climb**, or scrub to the beginning and end of the section you want and use **Set start here** and **Set end here** before analyzing. Playback still uses the original video timestamps. Dashed orange skeleton links indicate lower visibility. Gold marks projected center of mass. The optional blue and orange arrows represent image velocity and acceleration.
4. Review the contact timeline against the video. Each limb has its own row. Select an interval or use **Next uncertain** to check automatic contacts below the review threshold. Choose **No contact** to clear an interval or **Undo last correction** to restore it. Corrections carry over if you analyze the same open clip again. Changing height updates the 3D fit from cached landmarks.
5. Click a technique timestamp to jump to the footage. If enough placements were found, **Suggest alternative beta** can run ClimbGen's planner on those holds. **Download analysis JSON** saves the review without the video. To pick up again, open the original clip and use **Load saved review**. This restores the alignment, corrections, playhead and pose samples and recomputes the derived results locally.

The video stays local. The first analysis downloads Google's pinned MediaPipe Tasks Vision 0.10.21, its WASM runtime, and the version 1 Pose Landmarker Lite task. Google publishes the runtime under Apache 2.0 and identifies its underlying models as Apache 2.0. ClimbGen tries worker inference first and falls back to the main thread. The standalone HTML still needs network access for analysis assets. [Runtime package](https://www.npmjs.com/package/@mediapipe/tasks-vision/v/0.10.21), [official model configuration](https://github.com/google-ai-edge/mediapipe-samples-web/blob/main/src/tasks/pose-landmarker.ts), [runtime license](https://github.com/google-ai-edge/mediapipe/blob/master/LICENSE), [model license guidance](https://github.com/google-ai-edge/mediapipe-samples/issues/407).

MediaPipe samples about 12 frames per second. Intermediate video frames interpolate when adjacent tracked poses are available. Frame stepping uses presented media timestamps where supported and shows **Stepped by sample time** when it falls back. Motion estimates stop at tracking gaps. Camera movement, occlusion, overlapping holds, and nearby hands that have not gripped a hold can all produce false contacts. The board corners calibrate the face. The 3D model combines estimated landmark depth, height-based body proportions, and contact anchors, so poses and world COM depth remain approximate.

Cyan represents hand loads and purple represents foot loads in 3D. Gold shows gravity. The direction selector swaps the contact vectors between forces on the climber and forces on the holds. The estimates use body-weight units, an approximate static equilibrium, and temporal regularization across an unchanged stance. The equations allow multiple load distributions. Poorly observed, fast, and imbalanced frames show a reason when estimates are unavailable. Optional weight is retained in the export. Force values remain in body-weight units.

### Validation

Run `node --test tests/*.test.js` and `python3 scripts/build_pages.py`. To try the built app locally, run `python3 -m http.server 8765 --directory dist` and open `http://localhost:8765`. The regression suite covers projected board coordinates, variable timestamp stepping, missing landmarks, contact correction, COM, body constraints, force residuals, and existing generation and planning.

For a repeatable accuracy check, export the session before making corrections. Save manual labels with the media timestamps from the original video. Use contact intervals with `limb`, `id`, `start` and `end`; use `id: null` for a labeled gap. Use event labels with `category` and `start`, and optionally a `reviewedEvents` array of `[start,end]` ranges where event annotation is exhaustive. Then run `node scripts/evaluate_climb_analysis.cjs session.json annotations.json`. It reports coverage, sample-level contact accuracy and precision/recall, and event precision, recall and timing error within a 0.4-second matching window. Record separate runs for well lit, oblique, and occluded clips and label both static and dynamic moves. Re-export and rerun after corrections to check the effect of manual edits.
